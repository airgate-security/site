One gate to your infrastructure

Airgate guards the perimeter with L4 and L7 filters and publishes databases, clusters and servers to your engineers with access control by identity. Three parts, each usable on its own. Everything runs in your network.

Request early access How it works

Access and the perimeter are usually spread across many tools

  • Access

    VPN, SSH keys, shared database passwords. Every system has its own mechanism and its own exceptions.

  • Audit

    Who did what in a database or on a host is pieced together from several logs, and it is hard to show an auditor who could do what.

  • Perimeter

    The firewall, the WAF and block lists live separately and know nothing about each other.

  • Offboarding

    People leave, their access stays. Revoking it is manual work across a dozen systems.

Three parts, each works on its own

Start with the part you need now and add the others later. A node can run any one of them, or all three together.

L4

L4 filter in the kernel

Drops unwanted packets with XDP before the network stack and the applications see them. Allow and deny rules, rate and connection limits, protection against floods.

On its own: on a Linux host with kernel 5.8 or newer, even without the hub. Rules can come from a local directory.

About the L4 filter
L7

L7 web filter

A reverse proxy in front of your web services. It checks requests against the OWASP Core Rule Set, fingerprints clients and challenges suspicious ones. Your rules make the decision.

On its own: in front of any web service, also without the hub.

About the L7 filter
AC

Access control and resource publishing

Opens databases, Kubernetes, SSH and any TCP service to engineers with no inbound ports. Access goes by identity and policy, and every query and command lands in the audit log.

On its own: a node next to the resources and the hub, which signs sessions and keeps the audit. No filters required.

About access

Under one hub the parts share signals: an address caught by the L7 filter on one node can be dropped at L4 on every node of the fleet.

A hub that decides, nodes next to your resources

Engineers use the ag command line or a browser. The hub checks policy and keeps the audit log. Nodes sit next to clusters, servers and databases, and on the perimeter.

Nodes connect out

Each node opens an encrypted outbound tunnel to the hub. Resources behind it need no inbound ports.

Decided on the hub, enforced at the node

The hub checks the policy, issues a short-lived certificate for the session and writes the audit record. The node carries the decision out next to the resource.

No single point of failure

Run the hub as several replicas on PostgreSQL. If the hub is unreachable, nodes keep protecting the perimeter.

Access by identity, with a trail you can check

  • Your sign-in

    Any OIDC provider: Keycloak, Microsoft Entra ID, Okta. For simple setups Airgate ships with Dex.

  • Policies instead of keys

    Who may reach what, in one set of Cedar rules. Access is closed by default, rights follow groups, and a policy can be tested before it goes live.

  • No standing passwords

    Databases get a temporary user for each session instead of a shared password.

  • Access on request

    An engineer asks for access, an approver grants it for a limited time, and it expires on its own.

  • SSH under control

    Sessions are recorded. Every channel, from a shell to port forwarding, is authorized separately.

  • An audit log that shows edits

    Records are chained by hash, so a change made after the fact is visible.

Native clients, nothing to relearn

Engineers keep psql, kubectl, ssh and the other tools they use today. Airgate understands the protocol and records what matters in it.

One console for access and the perimeter

Nodes, sessions, audit events, bans and rules in one place, in English or Russian. Everyday operations are also available from the ag command line.

L4 and L7 filters

The filters run on the same nodes as access or on their own hosts, separately or together. With the hub, signals from every node come together and decisions apply to the whole fleet.

L4 in the kernel

  • An XDP program drops packets before the network stack and the application see them.
  • Allow, deny, rate limit and connection limit rules.
  • Per-source limits against floods. Connection limits count completed handshakes, so spoofed addresses cannot inflate them.
  • A detect mode for every rule shows what would be dropped before you enforce it.

L7 web filter

  • A reverse proxy on the node in front of your web services.
  • The OWASP Core Rule Set runs through Coraza and produces signals. Your rules make the decision.
  • TLS, HTTP and TCP fingerprints of clients.
  • A challenge for suspicious clients and lists of known crawlers.

Together under the hub

  • An offender is banned on the whole fleet or a zone, based on signals from the nodes.
  • Your own nodes are never blocked.
  • An emergency switch turns a rule set off in one action.
  • History and rollback of rules, metrics, a flood journal and notifications.

Built to stay inside your network

  • Self-hosted

    The hub and the nodes run on your servers. Your data does not leave your network.

  • No telemetry

    The product sends nothing home. Neither does this page: no counters, no outside fonts or scripts.

  • Works in closed networks

    No internet access needed. External data sources are optional.

  • Our own code

    Written in Go, with the kernel filter in eBPF. No third-party proxy in the data path.
